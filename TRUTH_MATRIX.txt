TRUTH MATRIX

1. Key contract / canonical technical identity
- Expected by TZ:
  - DB_KEY / RootKey / PARENT_KEY are primary command-flow keys.
  - pcct_uuid / RootId / ObjectUuid are compatibility aliases only at boundaries.
- Actual in code:
  - ODataEntityContracts centralizes alias field lists, but command payload and delta serialization still build root identity around pcct_uuid and broad fallback chains.
  - ODataChecklistPayloadMapper.normalizeSavePayload writes root.pcct_uuid as the active save identity.
  - DeltaFieldMappers.mapRootFields writes pcct_uuid, not DB_KEY/RootKey, as the outbound root key field.
  - DeltaPayloadBuilder.resolveRootKey still accepts RootKey, id, Key, pcct_uuid as near-equal command-flow candidates.
  - LockAdapter still maps rootId into ObjectUuid at the Gateway boundary, which is acceptable only as last-mile contract mapping.
- Status:
  - Partial / compatibility-tail-heavy.

2. Detail initial loading
- Expected by TZ:
  - Phase 1 = root + basic.
  - Phase 2 = checks + barriers asynchronously after initial render, chunked.
  - Phase 3 = attachments explicit only.
- Actual in code:
  - OpenDetailUseCase now requests root/basic only for initial open.
  - ODataChecklistReadRuntime.loadDetailRows fetches checks/barriers separately with $top/$skip chunking in pages of 20.
  - DetailPageFlow schedules second-phase row hydration after successful open without adding a new orchestration layer.
  - Attachments remain excluded from initial snapshot.
- Status:
  - Match.

3. Attachments metadata-first contract
- Expected by TZ:
  - Value is not an active source of truth.
  - Download/open prefers DownloadUrl/document handle/stream.
  - Persisted and session attachments are separated in state and UI.
- Actual in code:
  - DetailAttachmentOpenRuntime prefers DownloadUrl first, but still falls back to Value as a normal working path.
  - ODataEntityContracts.SELECTS.ATTACHMENT and SELECTS.ATTACHMENT_CONTENT still include Value.
  - ODataChecklistPayloadMapper.normalizeAttachmentRows filters rows by FileName && Value, making Value part of normal attachment normalization.
  - DetailAttachmentDeltaRuntime serializes staged attachments into value base64.
  - Persisted attachments now stay in detail>/current/attachments and session uploads stay in view>/sessionAttachments.
  - DetailAttachmentsBody.fragment.xml now renders session and persisted sections separately.
- Status:
  - Partial / compatibility-tail-heavy.

4. Attachment lazy loading
- Expected by TZ:
  - No attachments on initial detail open.
  - Persisted attachments loaded only by explicit action.
- Actual in code:
  - OpenDetailUseCase excludes attachments from initial snapshot fetch.
  - LoadAttachmentsUseCase is explicit.
  - OpenDetailUseCase no longer hydrates persisted attachments into view>/sessionAttachments on normal reopen.
- Status:
  - Match.

5. Delete pipeline
- Expected by TZ:
  - Canonical delete through aggregate modification pipeline.
  - No target direct OData DELETE.
- Actual in code:
  - GatewayClient.deletePath is unsupported as target flow.
  - AttachmentRepoRuntime.deleteAttachment is deferred only.
  - Root/child save path still goes through delta/save pipeline.
- Status:
  - Match.

6. Lock flow
- Expected by TZ:
  - acquire/status/heartbeat/release with ForceTakeover on acquire only.
  - ObjectUuid allowed only as Gateway contract field.
- Actual in code:
  - LockAdapter uses ObjectUuid, SessionGuid, optional TabSessionId and ForceTakeover on acquire.
  - Heartbeat/release use ObjectUuid + SessionGuid.
  - Component lock runtimes still compare rootId/ObjectUuid/RootId aliases during event handling.
- Status:
  - Partial but acceptable at Gateway boundary.
